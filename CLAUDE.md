## 🎯 Core Principles

### 1. File Management

**Avoid Bloat:**
- Keep files under 400 lines when possible
- Split large components into smaller, focused pieces
- Extract reusable logic into utility functions
- Remove dead code immediately

**Organization:**
- Use clear folder structure: `app/`, `components/`, `lib/`, `database/`, `docs/`, `scripts/`
- Group related files together (e.g., `components/event/`, `components/profile/`)
- Name files descriptively: `RSVPForm.tsx`, `NotificationBell.tsx` (not `Form1.tsx`, `Bell.tsx`)
- Keep documentation in `docs/` folder, not root (except README, SECURITY, etc.)

**When to Split Files:**
- Component > 300 lines → Extract sub-components
- Utility file > 400 lines → Split by functionality
- Too many exports from one file → Create subdirectory

### 2. Code Attribution

**Never include Claude in:**
- ❌ Git commits: No "Co-Authored-By: Claude"
- ❌ Code comments: No "Generated by Claude"
- ❌ Documentation: No attribution to AI
- ❌ File headers: No AI generation notices

**Instead:**
- ✅ Write code as if written by human developer
- ✅ Use standard commit messages
- ✅ Follow project conventions
- ✅ Credit only human contributors

### 3. Workflow Detection

**When to Suggest Workflows:**
- Performing same task 3+ times manually
- Complex multi-step process repeated
- Copy-pasting same commands
- Similar code patterns across multiple files

**How to Suggest:**
1. Notice the pattern
2. Say: "I notice we've done [X] multiple times. Would you like me to create a workflow/script for this?"
3. Wait for approval or objection
4. Only create if approved

**Examples:**
- Repeated database migrations → Migration script
- Similar component patterns → Component generator
- Manual deployment steps → Deployment workflow

### 4. Task Management

**All TODOs go in `TODO.md`:**
- No TODO comments in code (extract to TODO.md)
- No scattered action items across files
- Single source of truth for what needs doing
- Kanban board format with priorities

**Task Priority Levels:**
- 🔴 **Critical** - Blocks production, security issues, data loss
- 🟡 **High** - Important features, significant bugs, performance
- 🟢 **Medium** - Nice-to-have features, minor bugs, refactoring
- 🔵 **Low** - Polish, documentation, future considerations
- ✅ **Done** - Historical reference, completed work

**When Adding Tasks:**
1. Add to appropriate priority column in TODO.md
2. Include brief description and context
3. Reference related files/issues if applicable
4. Update when status changes

## 💻 Code Style Guidelines

### TypeScript
```typescript
// ✅ Good: Proper types, no any
interface Event {
  id: string;
  title: string;
  date: string;
}

function processEvent(event: Event): string {
  return event.title;
}

// ❌ Bad: Using any
function processEvent(event: any) {
  return event.title;
}
```

### React Components
```typescript
// ✅ Good: Small, focused, typed
interface EventCardProps {
  event: Event;
  onDelete: (id: string) => void;
}

export default function EventCard({ event, onDelete }: EventCardProps) {
  // < 100 lines
}

// ❌ Bad: Giant component
export default function EventPage() {
  // 500 lines of mixed concerns
}
```

### File Naming
```
✅ Good:
- components/event/RSVPForm.tsx
- lib/utils/formatDate.ts
- app/dashboard/page.tsx

❌ Bad:
- components/form1.tsx
- lib/utils.ts
- app/dash.tsx
```

## 🎨 Code Patterns

### Supabase Queries
```typescript
// ✅ Good: Typed, error handled
const { data: events, error } = await supabase
  .from('events')
  .select('*')
  .eq('host_id', userId);

if (error) {
  console.error('Failed to fetch events:', error);
  return [];
}

// ❌ Bad: Untyped, no error handling
const { data } = await supabase.from('events').select('*');
```

### Server Components
```typescript
// ✅ Good: Server-side auth check
export default async function DashboardPage() {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();

  if (!user) redirect('/login');

  // ... rest of page
}

// ❌ Bad: No auth check
export default async function DashboardPage() {
  // Anyone can access this
}
```

### Client Components
```typescript
// ✅ Good: Proper use of 'use client', error handling
'use client';

import { useState } from 'react';

export default function Form() {
  const [error, setError] = useState<string | null>(null);

  const handleSubmit = async () => {
    try {
      // ...
    } catch (err) {
      setError(err.message);
    }
  };
}

// ❌ Bad: Missing 'use client', no error handling
import { useState } from 'react';

export default function Form() {
  const [error, setError] = useState(null);
  // No try-catch
}
```

## 🚨 Security Requirements

**Always:**
- Validate user input server-side
- Use RLS policies on all tables
- Check authentication on protected routes
- Sanitize user-generated content
- Never commit secrets/credentials
- Use environment variables for sensitive data

**Never:**
- Trust client-side validation alone
- Use `eval()` or `dangerouslySetInnerHTML`
- Hardcode API keys or secrets
- Expose sensitive data to unauthorized users
- Skip authentication checks

## 📚 Documentation Rules

**When to Document:**
- New features → Add to `docs/`
- Complex logic → Comment explaining "why"
- Public APIs → Document parameters and returns
- Setup changes → Update README or setup guides
- Security changes → Update SECURITY.md

**When NOT to Document:**
- Obvious code (self-explanatory)
- Temporary code
- Work-in-progress
- Internal implementation details

**Documentation Location:**
- Feature guides → `docs/`
- API reference → Inline JSDoc comments
- Setup instructions → README.md or `docs/`
- Security info → SECURITY.md
- Project rules → claude.md (this file)
